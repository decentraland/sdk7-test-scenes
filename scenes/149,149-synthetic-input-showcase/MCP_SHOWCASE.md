# MCP_SHOWCASE.md -- driving script for `synthetic-input-showcase`

This is the script for the session that connects an agent to unity-explorer's embedded MCP
server and drives this scene live in front of the user. Read this top to bottom; each station
is self-contained and can be run independently and re-run at any time (see **Reset**, below).

**World coordinates** used below already include the scene's world offset
`(2384, 0, 2384)` (base parcel `149,149`). Local coordinates (what the scene code and its
`[INIT]` logs use) are always `world - (2384, 0, 2384)`.

> If a coordinate in this document ever disagrees with the scene, the
> `[INIT] MARK ... => local (...) world (...)` log lines are the authority -- they are computed
> from `toWorld()` at runtime.

**On `entityId`**: `click_entity`/`hover_entity` accept an `entityId`, but that id is the
Explorer's internal **Arch ECS** entity id (`list_scene_entities` returns `entity.Id`) and is
**not** the same id space as this scene's own CRDT entity ids (logged at `[INIT]`). The bridge
between them: a successful `click_entity`/`hover_entity` result reports **both** `entityId` and
`crdtEntityId`, so one world-aimed click on a target tells you its Arch id for subsequent
`entityId`-addressed calls -- see the README's "Substitutions" section. Every step
below therefore aims with explicit **world `x`/`y`/`z`**, which every tool accepts as an
alternative to (or in addition to) `entityId`. If you'd rather use `entityId`, call
`list_scene_entities` first and cross-reference against the `[INIT]` entity-id map in
`get_scene_logs`.

## Setup

1. Start the scene: `npm install && npm run start -- --mcp` from the scene folder -- this
   serves it on port 8000 and auto-launches the installed client with the MCP server on port
   8123. Log in when the client opens, then connect the driving session
   (`claude mcp add --transport http --scope user explorer http://127.0.0.1:8123/unity-explorer-mcp`)
   and poll `get_scene_state` until the scene reports `isReady: true`.
2. Call `get_scene_logs` once at the top -- the console should show:
   - `[INIT] synthetic-input-showcase starting`
   - `[INIT] base parcel 149,149 -- world offset (2384, 0, 2384); ...`
   - one `[INIT] <purpose> => entityId <id>` line per interactable
   - one `[INIT] MARK <label> => local (...) world (...)` line per floor mark / aim point
   Keep this transcript open -- every step below tells you which later log line to expect.
3. Take a baseline screenshot facing north down the S1 lane (this is the default spawn view).
4. Run the **Pre-flight** below before the stations -- it settles the coordinate space every
   positional step depends on, and its check 1 is the one a session is most likely to
   misread as a client defect.
5. **Read "Non-deterministic values" in the Driving notes before you measure anything.** Many
   quantities here (gait speeds, turn rate per `deltaX`, dot counts, aim-cone angles, scene-UI
   `crdtId`s) vary between clients and sessions by nature; every step asserts on an ordering or a
   shape that survives that, never on an absolute. **A measurement of yours that differs from a
   figure in this document is expected and is not a finding -- record it in
   `MCP_SHOWCASE_RESULTS.md` and do not edit this file to match.** Repeated passes "correcting"
   those numbers is the single largest source of churn this script has had.

## Pre-flight -- coordinate self-description (under a minute, run it first)

Everything positional in this script depends on one property: **a coordinate a tool hands you
can be fed back to a tool verbatim.** On a HiDPI display the client's screen (e.g. `2188x1231`)
is not the size of the screenshot you looked at, and getting that wrong misaims every
screen-space call in S8 and S10. **Two checks settle it.**

Open the S8 panel first -- **from `(2397, 0, 2396)`, looking north** (`move_to` there, then
`look_at 2397, 1, 2400`), a 3.5 m clear shot:

```
click_entity  x: 2397  y: 1  z: 2400
```

**Confirm `crdtEntityId 581` before going on.** The approach is not optional, and both ways of
getting it wrong return a cheerful `hit: true` on the wrong entity (measured):

| Where you stand | What you actually hit |
|---|---|
| **east** of the panel, e.g. `(2410, 0, 2400)` | `582` -- **RESET ALL STATIONS**, which sits at `x 2403` on the same line `z 2400`. It fires a reset |
| **south of `z 2393`**, e.g. `(2397, 0, 2389)` | `590` -- the **S10 STROKE canvas**, which spans `x 2396.2..2399.8` and so covers this aim's `x`. It arms a stroke |
| `(2397, 0, 2396)` | `581`, the S8 toggle -- correct |

`z 2396` is the sweet spot: it is north of both S10 canvases (`z 2393`) and south of the button,
so nothing is in the line. If you get any other id, reposition rather than re-issuing -- see the
rule under **Reset**.

Then `ui_list stack: sdk` -- the result carries `screen: {width, height}`, and every element a
normalized `center` inside 0..1 beside its `screenRect`.

1. **A `center` fed to `click_at` resolves to that element -- and is refused.** Pass one
   button's `center` verbatim: expect `hit: false` with `blockedByUi: "the scene's UI (crdtId
   <that element's id>)"`, and **no** scene log. Repeat with a second button: the cover must name
   *that* button's id. Naming the right element twice is the proof the round trip is exact --
   a misaim would name a different element or none. `click_at` rays into the 3D world and has no
   SDK-UI delivery leg; **activating scene UI is `ui_click`'s job** (`ui_click stack: sdk crdtId:
   <id>` on the same button logs the click). A `blockedByUi` here is the check passing, not a
   defect -- do not "fix" it by adding `force: true`, which aims *past* the UI into the world.

   > If this fails, check the arithmetic before blaming the aim: `center.x` must equal
   > `(screenRect.x + screenRect.width / 2) / screen.width`. A `center` that does not satisfy that
   > is the bug; a correct `center` naming the wrong element is a different one.

   > **A UI-cover refusal leaks nothing to the scene root, unlike S4's ray misses.** S6's board read
   > `IA_POINTER: 0` immediately after both refusals above, while S4's three `x/y/z` ray misses each
   > post one `PET_DOWN` to the root (`IA_POINTER: 3` there), matched by an `UP` on a later tick as
   > S4's own blockquote describes. The cover check runs *before*
   > any edge is posted; a ray miss is refused *after*. So this check costs you no counter drift and
   > no S10 arming at all -- run it first, freely, and read S4's leak as specific to ray misses.
2. **`screenshot` states the screen it downscaled from.** Its caption reads
   `1280x720 (screen 2188x1231)`, and that `screen` matches `ui_list`'s exactly. Try a second
   `maxWidth` to confirm only the capture size moves.

If either check fails, stop and report it before running the stations -- every later positional
step inherits the same coordinate space.

> **Two checks, and no more -- but do not trim these two.** The rest of the coordinate contract is
> already covered inside the stations, so the pre-flight does not repeat it: a `ui_drag` between
> two `center`s **is** S8 step 8 (which asserts `path: "sdk"` on the first try), and the
> `screenRect` + `center` + `screen` triple on every `ui_click`/`ui_scroll`/`ui_set_text` result is
> observed for free throughout S8 and S9 (see S8 step 2). The `center`-vs-`screenRect` arithmetic
> is a diagnostic for check 1 rather than independent coverage, which is why it sits inside it.
> **Never drop checks 1 or 2 on the grounds that they keep passing** -- catching a regression is
> exactly what they are for.

## S1 -- Locomotion lane

Proves: **(1)** real locomotion pipeline, collisions, speed-by-`kind`. **(3)** `walk` does not
emit `IA_FORWARD`.

1. Face north (default spawn orientation already does this) and check the S1 readout board at
   world `(2388, 3.6, 2401.5)` -- the far end of the lane, next to the end wall (`S1_READOUT`
   is local `(4, 3.6, 17.5)`). It is *not* above the spawn point -- at that position it would sit
   behind the camera from every viewpoint the lane is walked from.
2. From the 0m marker `(2388, 0, 2385)`, walk north at `walk` speed:
   ```
   walk  directionX: 0  directionY: 1  seconds: 1.2  kind: walk
   ```
   Expected result: `distance` well under the `seconds * speed` ceiling for a fast gait --
   this is the slowest bucket (~1.5 m/s per `AvatarLocomotionSettings` defaults), so expect a
   couple of metres, short of the "4m" floor marker at world `(2388, 0.05, 2389)`.
   Expected log: `[S1-LOCOMOTION] burst finished: distance=<N>m over <N>s avgSpeed=<N>m/s sustainedSpeed=<N>m/s bucket=walk`
   -- note the `over <N>s` field, which is the burst's *measured* duration and runs a little under
   the `seconds` you asked for.
3. `move_to` back to the 0m marker and repeat with `kind: jog`, then again with `kind: run`, then
   compare `distance` and `sustainedSpeed` across the three -- `run` should cover visibly more
   ground per second than `jog`, which covers more than `walk`. **All three bursts use the same
   `seconds: 1.2` from the same mark**, which is what makes them comparable.

   > **Why 1.2s and not 2.** The lane is only ~17.5m from the 0m marker to the end wall, and at the
   > faster gait speeds a 2s jog covers ~20m and a 2s run ~25m -- both end clipped against the wall,
   > which voids the comparison. 1.2s tops out around 9-10m and fits. If your client is faster
   > still and the run burst reaches the wall, shorten all three equally rather than only that one.

   A `move_to` between bursts logs a `teleport detected ... ignored` line instead of a phantom
   superhuman burst (each followed by a spurious 0.08m/0.03s micro-burst line -- harmless, ignore
   it).

   **The assertion, in full** -- three 1.2s bursts from `(2388, 0, 2385)` facing north:

   1. **`sustainedSpeed` is strictly increasing** walk < jog < run, with a clear gap at each step
      (the jog-run gap has never measured below ~1.5 m/s).
   2. **`distance` is strictly increasing** the same way, and every burst fits the lane
      (< ~10m from the 0m marker).
   3. Nothing else. **`bucket=` is not an assertion** -- see below.

   The first two hold on every pass on record. That is the whole of step 3; do not reconcile the
   absolute speeds against anything, including this document.

   > **Do not assert on `bucket=` at any burst length, and do not refit the classifier to make it
   > assert.** The thresholds are `WALK_MAX_MS = 3` and `JOG_MAX_MS = 12`
   > (`src/stations/s1_locomotion.ts`), and two independent effects break the label -- neither of
   > them a scene bug. Under ~1s the EMA has not converged. And at *any* length the tier speeds may
   > sit below 12 on your client, which drops the whole `run` tier under the threshold so that
   > `run` reports `jog`. Both readings have been observed, as has the mirror image (everything
   > reporting `run`) on a faster client. **A `run` burst labelled `jog` is expected output, not a
   > finding** -- and fitting `JOG_MAX_MS` to one session's numbers is what produces the mirror-image
   > drift, so leave it alone.
   >
   > Record your pass's speeds in `MCP_SHOWCASE_RESULTS.md`, not here -- see
   > **Non-deterministic values** in the Driving notes.
4. Walk all the way into the end wall:
   ```
   walk  directionX: 0  directionY: 1  seconds: 6  kind: run
   ```
   Expected result: `endPosition` stops at/near world z `2402.5` (the wall face) even though
   6 seconds at run speed would cover much more distance in the open -- **collision applied**.
   Screenshot: player pressed up against the wall, past the "16m" marker.
5. Press forward the "wrong" way to show the `IA_FORWARD` divergence:
   ```
   walk  directionX: 0  directionY: 1  seconds: 1
   ```
   Then read the S1 readout board (`get_entity_details` on its engine id -> `PBTextShape.text`; a
   screenshot cannot resolve it from the lane): it prints
   `global IA_FORWARD count: 0 (see S6)`. `walk` moved the player but the counter stayed at 0.
   (An omitted `kind` is **jog**, not walk -- that is the tool's documented default: measured 6.87 m
   in 1 s, `sustainedSpeed 9.90`, `bucket=jog`. It does not matter here -- the assertion holds for
   any gait -- but start from the 0 m mark so the burst has room.)
6. Now:
   ```
   press_input  action: forward
   ```
   Screenshot the S1 (or S6) readout again: `global IA_FORWARD count: 1` -- proves divergence
   **(3)**: only `press_input FORWARD` increments the SDK input-action counter; `walk` never
   does, even though both move-shaped inputs exist.

## S3 -- Freeze zone (`InputModifier`)

Proves: **(2)** InputModifier applies to `walk` exactly like WASD; `ignoreInputModifiers`
escapes it; the run-only sub-zone shows the degrade-through-fallback case.

1. Walk from the lane entrance into zone A (world center `(2395, 0.05, 2404)`, spans world
   x `2393..2397`, z `2402..2406`):
   ```
   walk  directionX: 0  directionY: 1  seconds: 2  kind: run
   ```
   **Start from `(2395, 0, 2398)` facing north** (`look_at 2395, 1, 2410`) -- 4 m of run-up south of
   zone A's near edge at `z 2402`, all of it clear ground outside both zones. The burst does not run
   its full 2 s: it enters the zone and the freeze bites, so it stops a metre or two in (measured
   6.09 m of travel ending at `z 2404.09` on one pass, 5.02 m ending at `z 2403.02` on another,
   against the ~20 m a free 2 s run covers) -- that truncation is the first half of the proof,
   before step 2 even runs. Either landing spot is inside zone A, which is all the step needs.
   Expected log: `[S3-FREEZE] zone A entered (#1) -- InputModifier disableAll+disableJump applied`.
   Screenshot: the S3 readout at world `(2395, 3, 2407)` shows `modifier: zone A: disableAll + disableJump`.
2. While standing in zone A, try to walk further:
   ```
   walk  directionX: 0  directionY: 1  seconds: 2  kind: run
   ```
   Expected result: `distance` ~0 -- the freeze applies to `walk` exactly as it would to WASD.
3. Now escape it:
   ```
   walk  directionX: 0  directionY: 1  seconds: 0.7  kind: run  ignoreInputModifiers: true
   ```
   Expected result: `distance` > 0 again -- `ignoreInputModifiers` bypassed the scene's lock.

   > **Keep this burst short — 0.7s, not 2s.** Zone B's north end (`z 2416`) *is* this 2x2 scene's
   > north parcel boundary, so a 2s escape run north out of zone A carries the player clean off the
   > scene (measured ~17m of travel against ~11m of room). Off-parcel every subsequent click fails
   > with "no running current scene". 0.7s reliably lands the player **inside zone B** (whose near
   > edge is `z 2407`) and short of the parcel edge -- read `endPosition.z` back rather than
   > predicting it, since the distance covered scales with your client's run speed -- which
   > also gets you step 4's zone-A-exit and zone-B-entry **on foot** in the natural order — better
   > evidence than step 4's `move_to`, whose two log lines can arrive in either order.
4. Walk out of zone A (south, back the way you came) and confirm the log
   `[S3-FREEZE] zone A exited`, then `move_to` the zone B entry mark at
   world `(2395, 0, 2407.5)` and walk north into the zone (a 9m corridor, world z `2407..2416`).
   Expected log: `[S3-FREEZE] zone B entered (#1) -- InputModifier disableRun applied (walk/jog still work)`.
   **`move_to` between zones is safe but not order-preserving**: a teleport that crosses both
   volumes can deliver the destination's `enter` BEFORE the origin's `exit` — an order a walking
   player never produces. **Which order you get is not guaranteed, so assert on neither**: both
   have been measured in a single session, one per direction of travel (zone A -> zone B gave the
   natural `exit` then `enter`; zone B -> zone A gave the reversed `enter` then `exit`). The scene
   recomputes the `InputModifier` from zone occupancy on every event, so the modifier ends up
   correct either way — verify it on the readout rather than inferring it from the log order — but
   any scene that writes the modifier directly from its handlers would be left unfrozen whenever
   the reversed order comes up.
5. In zone B, measure the degradation. **`disableRun` degrades run to jog — it does not stop
   the player**, so this step compares speeds, not distances, and the burst must be long enough
   to leave the acceleration ramp (that is why the zone is a 9m corridor and not a 4m pad: a run
   burst crossed the old pad in ~0.25s, entirely inside the ramp, and an in-zone burst read the
   same as a control burst outside it). From the zone B entry mark, facing north:
   ```
   walk  directionX: 0  directionY: 1  seconds: 0.8  kind: run
   ```
   Expected log (S1's classifier reports the sustained speed): a `sustainedSpeed` clearly below the
   free-run control in step 6 — the run request was degraded to the jog tier.

   > **0.8s, not 1s** — at this client's speeds a 1s run burst covers ~10m and cannot be contained
   > in the 9m corridor at all. 0.8s is still well clear of the acceleration ramp: a measured burst
   > reached `sustainedSpeed 9.51` within 0.49s, so the ramp is far shorter than the corridor
   > budget assumes.
   >
   > **Do not judge this step by the `bucket=` label — this station cannot.** Its 9m corridor caps
   > the burst at 0.8s, which is below the ~1s the classifier's EMA needs to converge, so every
   > 0.8s burst under-labels: at `JOG_MAX_MS = 12` all three read
   > `bucket=jog`, where under the old threshold of 9 all three read `run`. Neither reading
   > separates them. Compare sustained speeds, and take step 6's *two* controls.
6. Controls: leave the zone and repeat the identical 0.8s burst — then run it a third time with
   `kind: jog`.

   > **Take the controls SOUTHWARD from `(2402, 0, 2412)`, not northward from
   > `(2400, 0, 2407.5)`.** A 0.8s free run covers ~10m; from z 2407.5 that lands at ~2417.5,
   > past the scene's north edge at z 2416, and off-parcel every later click fails with "no
   > running current scene". `(2402, 0, 2412)` facing south (`look_at 2402, 1, 2400`) is clear
   > ground with ~10m of room and is outside both zones. This is the same hazard step 3 warns
   > about, one step later.

   Reference measurement (in-zone from the zone B entry mark facing north; controls south from
   `(2402, 0, 2412)`):

   **The assertion is a shape, not three numbers.** Take all three at the same `seconds: 0.8` and
   compare `sustainedSpeed`:

   ```
   in-zone run  ~=  free jog     (within a few tenths of a m/s)
   in-zone run   <  free run     (by ~1.5-2 m/s)
   ```

   The run request was degraded to the jog tier. **The jog control is what makes it
   unambiguous** — without it, "the in-zone run was slower" could just be the acceleration ramp.
   Both lines hold on every pass on record; the absolute speeds move ~20% between clients and

   calibration.
7. Also confirm `kind: walk` inside the zone is untouched (`bucket=walk`), i.e. the lock degrades
   the run tier only.

>

>    (`entityId`, or `x/y/z`): with it the reticle is held on the target for the gesture, which is
>    the only *reliable* way to bind. `look_at` followed by an unaimed `press_input` is not a
>    substitute — but it is not inert either, and that is the trap.

>    Measured live: an unaimed `press_input action:forward`, with no `entityId` and no `x/y/z`, returned
>    `entityBound: true` on `crdtEntityId 584` (the S9 world toggle) at `distance 5.54` — and

>    `entityBound: false` and the expected root broadcast. The binding is not filtered by action:
>    a `forward` press bound to a button that exists to take a pointer click. `cursorState` is
>    `Free` and `pointerLocked` is `false` throughout, so the reticle does rest somewhere.

>    **pitch the view into open sky with `camera_look deltaX: 0 deltaY: 8 seconds: 1.5`, then

>    reliably clear the reticle. A later run needed a second call 3 times out of 4 (the first stopped
>    at -22 to -27 degrees, i.e. x around 333-338), and only once did a single call suffice. Repeat
>    until x is near 306 (-54 degrees, about the third-person clamp). A step that reports
>    `entityBound: true` when you passed no aim has measured nothing; re-clear and repeat rather than
>    recording it.

## S10 -- Paint surface (clicks and drags become geometry)

Proves: **(10)** a pointer position is usable as *content*, not just as a hit test. The station
turns pointer positions into spheres by the two paths the synthetic-input layer can reach a
world surface with, and they fail in different ways, so each gets its own canvas:

- **STAMP canvas** -- an ordinary `pointerEventsSystem.onPointerDown`. Every `click_entity` /
  `click_at` / aimed `press_input` paints exactly one dot at the hit position the event itself
  carries (`PBPointerEventsResult.hit.position`). No held button needed; fully deterministic.
- **STROKE canvas** -- the `0,5-primary-cursor-info` pattern: an `IA_POINTER` down/up pair marks
  the button held, and while it is held the station raycasts along
  `PrimaryPointerInfo.worldRayDirection` every ~60 ms and drops a dot wherever the ray lands.
  This is the one that needs the pointer to stay **down across several frames** — and, because
  that ray is built from the camera, the one that needs the camera to *turn* while it is held.
  It arms on a pointer-down on the canvas itself or on an `IA_POINTER` scene-root broadcast.

| Element | World center | Extent | Role |
|---|---|---|---|

| STAMP canvas | `(2394, 2.1, 2393)` | x `2392.2..2395.8`, y `0.8..3.4` | one white dot per click |
| STROKE canvas | `(2398, 2.2, 2393)` | x `2396.2..2399.8`, y `1.0..3.4` | a coloured trail while held |
| DECOY strip | `(2398, 0.6, 2393)` | y `0.2..1.0`, directly under the stroke canvas | collidable, **never** painted |

   Tune the turn so the ray stays on the canvas: `deltaX` is the same unit `camera_look` takes, and
   **how far that unit turns you varies several-fold between sessions** (see **Driving notes** on
   turn rate), so **size `deltaX` from your own calibration pan, not from a number in this
   document.**

   **Aim for a sweep of roughly 40-50 deg of yaw over ~3s.** At the rates measured so far that has
   meant `deltaX: 1  seconds: 3`; at ~3 deg/s per unit it would take `deltaX: 5`. The dot count
   follows from that choice, so it is an *outcome*, not a target: a slow sweep paints a dense
   stroke (a dozen or more dots over ~1.8m of surface), while a fast one drags the ray off the
   canvas between samples and paints a sparse handful. Prefer the slower sweep.

   The **assertions** are: `pressed.hit: true` on the stroke canvas, `swept: true`, a `released`
   leg, the three log lines below, and **N > 1**. The value of N is not an assertion. A sweep that
   leaves the canvas is not a failure either — it is step 4's negative case arriving early, and the
   logs say so.

   **Read N carefully, and read *which* single-dot message you got.** If N is 1 the station
   distinguishes two very different causes, and they are not interchangeable -- treating the second
   as the first sends you hunting the wrong bug:

   | Log line | Cause |
   |---|---|
   | `STROKE #N was a single dot -- the pointer was not held across frames. A drag has to keep IA_POINTER down over several updates ...` | the press and release landed inside **one drain window**, so the gesture was delivered as a click. The hold itself was too short |
   | `STROKE #N was a single dot even though the pointer was held across <N> ray samples -- the ray never moved, i.e. the camera did not turn while the button was down ...` | the hold **was** long enough and sampled many times, but the **camera never turned**, so the ray stayed on one spot. This is the split-gesture result -- see the negative-case table below |

   The station picks between them on `samplesThisHold` (`src/stations/s10_paint.ts`). Either way
   this is the measurement this station exists for — report it as the result, not as a scene
   failure.

   > **A gesture too short to hold the pointer usually does not reach the first row at all — it
   > opens no stroke.** The sampled ray needs a few frames to park on the pressed pixel, so a
   > sub-frame gesture's first sample or two miss the canvas and the honest line you get is
   > `hold ended without painting -- N ray samples were taken and none hit the stroke canvas`,
   > with **no `STROKE #N started` line before it**. Measured across four such gestures — two
   > `click_entity` down/up pairs on the canvas, an instant aimed `press_input action: pointer`,
   > and a `sweep_pointer` at `seconds: 0.1`. The first row needs a stroke to be *open*, i.e.
   > exactly one sample that **did** hit the canvas, and no gesture on the tool surface has been
   > found that produces it. So read that row as the message's meaning, not as a target to
   > reproduce: for a real short-hold diagnosis, `hold ended without painting` is the line to
   > expect, and it is not the same thing as S4's refused-click leak, which reaches it from an
   > unaimed root broadcast rather than from a press on the canvas.

   > **Do not use `ui_drag` here.** A device drag over the world reaches no UI and paints nothing:
   > measured twice (20- and 45-frame drags over this canvas, cursor `Free`) it returned `ok:true`
   > with no stroke and no camera movement (yaw `359.98`, pitch `351.82`). The result now says so —
   > `pointerOver: {start:"world", end:"world"}` plus an `info` line — because the gesture
   > verifies no target. The left button is also the camera-pan binding (for a human too), so the
   > same call can instead turn the camera, and then it fails with "the drag panned the camera
   > instead of dragging"; with the cursor locked it fails up front. Either way nothing is dragged
   > in the world — `ui_drag` is for UI. The station arms from a pointer-down on the canvas itself
   > *or* from an `IA_POINTER` scene-root broadcast read with a timestamp watermark, so an unaimed
   > hold arms it too. **It deliberately does not arm from the entity-less `inputSystem.isTriggered`,
   > which cannot read the scene root at all** (`RootEntity` is `0`, falsy-zero guard — the trap S6
   > documents); if a future edit swaps the gset read for an `isTriggered` call, this step becomes
   > undrivable.
   >
   > **`sweep_pointer` is the only gesture that actually paints a stroke** -- the alternatives were
   > measured and they are **not** equivalent, despite arming identically:
   >
   > | Gesture | Arms | Ray samples | Result |
   > |---|---|---|---|
   > | `sweep_pointer` aimed at the canvas | yes | many, ray moves | a real stroke (11-16 dots) |
   > | **aimed** `press_input ... x/y/z holdSeconds: 2` + parallel `camera_look` | yes (canvas pointer-down) | **25-27 taken, all on the same spot** | `STROKE #N ended -- 1 dots over 0.00m` |
   > | **unaimed** `press_input action: pointer holdSeconds: 2` + parallel `camera_look` | yes (scene-root broadcast) | 27 taken, **and where they land depends on where the free pointer was last parked** | see below |
   >
   > **The unaimed row has two outcomes, and which one you get is not about the press.** The free
   > pointer stays wherever the last aimed gesture parked it, and neither `camera_look` nor `look_at`
   > moves it -- so:
   >
   > - Run the unaimed hold **after an aimed gesture on the canvas** and the parked pointer is still on
   >   the canvas: 27 samples all re-hit that one spot and you get
   >   `STROKE #N ended -- 1 dots over 0.00m`, i.e. the aimed row's result. Measured this way.
   > - Run it with the pointer parked anywhere else (e.g. from `(2403, 0, 2396)` after clicking a world
   >   button, or after S4's misses) and you get
   >   `hold ended without painting -- 27 ray samples were taken and none hit the stroke canvas`.
   >   Measured this way too, in the same session.
   >
   > Either way **nothing is swept** -- one dot or none -- which is the point of the row. Pitching the
   > camera into sky clears the *view*, not the cursor, so do not read "I aimed at the sky" as "the
   > pointer is off the canvas".
   >
   > **`PrimaryPointerInfo.worldRayDirection` is populated in all three cases** -- the theory that
   > it was never written is wrong, and the station's `no-ray samples` counter reads
   > `0` for every gesture above.
   >
   > **Why the split gesture fails: the two calls never overlap.** MCP tool calls are
   > **serialised** by the server, so a `press_input ... holdSeconds: 2` issued "alongside" a
   > `camera_look` runs to completion *before* the turn starts, and the camera is stationary for
   > the entire hold. Measured with a detached out-of-band yaw poller (~135ms
   > cadence): the hold ran 10:10:28-30 (`STROKE #4 started`/`ended`) with yaw pinned at
   > **29.73 for 60+ consecutive samples spanning the whole hold**, and the turn then ran
   > 10:10:32.45 -> 10:10:34.59 (`29.73 -> 53.85`) — starting **2.4s after the hold ended**.
   > An unaimed press additionally parks the pointer wherever the free cursor sits, so its ray
   > never crosses the canvas at all.
   >
   > This **withdraws an earlier client defect report** ("an aimed press parks a ray that is not
   > re-derived as `camera_look` turns the view"). That diagnosis assumed the calls overlapped;
   > they did not, so the gesture cannot test re-derivation and nothing is established about it.
   > `sweep_pointer` is the only gesture that holds press + turn + release inside one call, and
   > therefore the only one that can sweep. Use it; keep the split gesture only as the negative
   > case above.
   >
   > **Measuring overlap, if you ever need to:** reading `get_player_state` yaw before and after
   > does **not** work — both results arrive in one batch, so there is no moment at which you can
   > sample "as `press_input` returns", and the naive before/after reading (`29.74` then `54.28`)
   > says the opposite of the truth. A poller issued in the *same* tool batch does not work
   > either: it is served for its full window before the gesture is dispatched at all. Only an
   > already-running **detached background** poller samples the hold.
   >
   > Do **not** read `off-canvas samples (decoy / miss)` as "was a sample taken". It only counts
   > misses once a stroke is already active, so it stays `0` through a hold that sampled 27 times
   > and missed every time -- the exact reading that has sent sessions down the wrong path. The
   > `hold ended without painting -- N ray samples were taken ...` log line is the honest channel.

4. **Sweep off the canvas onto the decoy (the negative case).** Same gesture, but turn far enough
   (or downward) that the ray leaves the canvas onto the red strip below it. **Re-`look_at` the canvas
   first** -- step 3's sweep left the camera turned ~24 deg away, and only a press that lands *on
   screen* parks the pointer:
   ```
   look_at        x: 2398  y: 2.2  z: 2393
   sweep_pointer  entityId: <stroke canvas>  deltaX: 2  deltaY: -6  seconds: 2
   ```
   **`deltaY` is subject to step 3's calibration exactly as `deltaX` is -- size it from your own
   pan rate, not from the number above.** What the step needs is roughly 25-30 deg of downward
   pitch: enough to walk the ray off the canvas's bottom edge (world y `1.0`) onto the strip below
   it. Undershoot and every sample stays on the canvas and the stroke-end line reports
   `0 samples landed off the canvas` -- the negative case simply did not run, so re-drive it with
   more pitch rather than recording it as a pass. Overshoot (a fast client on the number above)
   and the ray leaves the whole assembly.
   Expected logs: the stroke starts normally, then up to three
   `[S10-PAINT] stroke sample left the canvas (hit entityId ...) -- no dot painted` lines
   (the rest are counted, not logged -- the ray fires ~16x/s), and the stroke-end line reports
   the off-canvas total. Screenshot: **no** spheres below the canvas's bottom edge. If dots do
   appear on the red strip, the ray is not following the pointer -- it is spraying at whatever is
   in front of the camera.
5. **Pool cap.** Keep painting past 40 total dots. **Read `live dots: N/40` off the readout and
   budget from there — never assume how far steps 2-4 left you**, because that total is the sum of
   your sweeps' dot counts, which are an outcome of your turn rate (passes on record have arrived
   here holding anywhere from 13 to 25). Repeat step 3's sweep until the log below appears; from
   ~25 a single dense sweep is usually enough. Expected log, once:
   `[S10-PAINT] dot pool full at 40 -- painting now recycles the oldest dot`. The readout's
   `live dots` sticks at `40/40` while `recycles` climbs, and the oldest dot visibly moves to the
   newest position. A DCL sphere primitive is 804 triangles and a 2x2 scene's whole budget is
   40,000 -- an uncapped painter would blow it in about a minute of dragging.
6. **Clear:** `look_at 2392, 1, 2390` first -- from the stand mark this is a 4 m shot west, clear
   of both canvases (they sit at `z 2393`, north of the line):
   ```
   click_entity  x: 2392  y: 1  z: 2390
   ```
   Expect **`crdtEntityId 592`**.
   Expected log: `[S10-PAINT] canvas cleared (world button) -- clear #1`. Readout: `live dots: 0/40`
   with every other counter untouched. (`RESET ALL STATIONS` also wipes the dots, but zeroes the
   counters with them.)

## Driving notes (hazards that are not tied to one station)

### Non-deterministic values -- do NOT reconcile these, and do not add your own

**Read this before "correcting" any number in this document.** This script has been re-driven
many times, and the single largest source of churn was not a defect in the scene, the client or
the steps -- it was passes finding a measured number different from the one written down and
dutifully updating it. That produced tables that grew a column per session, each one true of
exactly one machine and misleading everywhere else, and it displaced the *invariants* those
sections exist to state.

The quantities below **vary between clients, sessions or panel opens by design or by nature.**
No step asserts on their absolute value; every step asserts on a relationship, an ordering or a
shape that survives the variation. If your measurement differs from a figure quoted here:
**that is expected, it is not a finding, and this document does not need editing.** Record it in
`MCP_SHOWCASE_RESULTS.md`, which is where per-pass evidence belongs.

| Quantity | Varies by | Assert on this instead |
|---|---|---|
| `sustainedSpeed`, gait tier speeds | client, ~20% | ordering walk < jog < run (S1), and the in-zone/free-jog/free-run *shape* (S3) |
| `bucket=` labels | derived from the above | nothing -- explicitly not an assertion (S1 step 3, S3 step 5) |
| `deltaX`/`deltaY` degrees per unit | client, **5x** | calibrate once per pass; see the turn-rate note below |
| Stroke dot counts, `longest`, `live dots` en route to the cap | your turn rate | N > 1 for a real sweep; `live dots` read off the board, never assumed (S10 steps 3, 5) |
| Aim-cone entry angles (`entered aim (angle N)`) | orbit-boom settling, run to run | each marker enters **once** and does not flap; the 18 deg cone plus 30 deg release is what buys that (S7) |
| `aimErrorDegrees` on close, slightly-downward aims, and its rig-limit `warning` | camera pose | let the following `click_entity`/`hover_entity` be the test; meaningful only above ~10 deg |
| `held <N>ms` on the charge commit | how long you waited | that a commit fired at all (S4 step 2) |
| Scene-**UI** `crdtId`s (`ui_list`, S8/S9) | every panel open, non-monotonically | match by `center`; never carry an id across a panel open |
| Whether the chat feed's transparent viewport covers `y 0.5366` | screen size and chat state | issue the plain click first and read the result (S9 step 8) |
| Client `averageFps` | machine | nothing; it is context for the turn rate at most |

**What *is* stable, and therefore worth asserting:** world coordinates and the `[INIT] MARK`
lines; the scene's own **entity** `crdtEntityId`s (`512`-`592`, allocation-ordered at `[INIT]` and
identical across reloads -- unlike scene-UI ids); every log line's text; each element's normalized
`center` at a given screen size; the exact wording of the client's refusal messages; and every
structural claim -- which path a tool takes, that an entity-bound edge suppresses the root
broadcast, that a cover refuses a click, that a disabled input refuses a write.

> **Corollary for anyone editing this file: prefer deleting a number to updating one.** If a
> figure is load-bearing, state the invariant and drop the figure. If it is illustrative, mark it
> as one session's observation and never append a second. A table with one column per pass is the
> smell this section exists to prevent.

- **Never write a coordinate with a trailing `.0`.** `click_entity x:2393 y:3.0 z:2393` arrives as
  the *string* `"3.0"` and the aim is refused:
  `"x, y and z must all be numbers to aim at a world point. (y arrived as string \"3.0\", not a
  number)"`. Write `3`, not `3.0`. **This trap IS reachable from Claude Code's native MCP tools** --
  reproducible first try by writing `y: 3.0` in an ordinary `click_entity` call: the harness
  serializes the literal `3.0` and the coercion to a string happens on the way out, before the
  request exists. **Do not rely on your client to normalize it for you.** The message names the
  offending argument and what arrived, so read it as a wrong *type* rather than a missing argument;
  an older client instead opens with `"Provide entityId, or a full x/y/z world aim point, or both."`,
  which points at the wrong cause.
- **`move_to`'s `lookAtX/Y/Z` is a no-op** on this client -- it leaves camera yaw and player
  rotation untouched, and the result carries no `cameraRotationEuler` to tell you so. Since `walk`
  is camera-relative, trusting it sends a burst in whatever direction the camera already faced; a
  control run intended southward went north and carried the player off the scene's north edge
  (`scene: null`, after which every click fails with "no running current scene"). **No step here
  uses it -- set facing with `look_at` only.**
- **A `deltaX`/`deltaY` unit does NOT turn the camera a fixed number of degrees -- calibrate before
  trusting any pan in this script.** The same `camera_look` call turned **five times further** on
  clients, and `sweep_pointer` shares the unit. Rates between **~3 and ~16 deg/s per unit** have
  both been measured, a 5x spread; within one session the rate is stable to about +/-15% across
  both tools and every `deltaX`/`seconds` combination, so **one measurement calibrates your whole
  pass.**

  **The procedure, which is the only durable part of this note:**

  ```
  camera_look deltaX: 6  deltaY: 0  seconds: 1.5     # a throwaway pan
  ```

  Both tools return `cameraRotationEuler`, so divide the yaw change by `deltaX * seconds` and size
  every `deltaX` in S7 and S10 from *that*. Do not reuse a number from this document or a previous
  pass; do not treat a rate unlike the last one as a finding.

  Only steps asserting on a specific turn are affected (S7 step 3, S10 steps 3-5). Reticle-clearing
  (`deltaY: 8`) is unaffected -- it runs into the pitch clamp either way, which is why that step
  says to read `cameraRotationEuler.x` back rather than counting calls.

  The likeliest mechanism is a per-frame delta accumulating over more frames on a faster client
  (the fast sessions averaged 165-169 fps), but it is **unproven** -- no slow-fps session has been
  measured -- so treat the *variability* as the fact and don't refine the hypothesis without a
  counter-example.
- **MCP tool calls are serialised by the server**, so two calls issued "together" never overlap.
  A `press_input ... holdSeconds: 2` and a `camera_look` in one batch run one after the other, with
  the camera stationary for the whole hold. This is why `sweep_pointer` exists and why the split
  gesture cannot paint a stroke (S10 step 3). It also means you cannot measure the overlap from
  inside your own calls -- only a detached background poller can.
- **`look_at`'s rig-limit warning is noisy at small angles.** It emits *"the camera stopped short of
  the point (a rig limit, e.g. the third-person pitch clamp)"* on close, slightly-downward aims that
  are in fact fine -- seen at `aimErrorDegrees` of 3.1, 5.5, 5.6 and 9.9 on the S8 toggle, the offset
  pivot, the big `click_at` target and hover targets A/C, every one of which the following
  `click_entity`/`hover_entity` hit correctly. Contrast S7 step 4's genuinely unreachable MARKER-U at
  **33.8**. Treat the warning as meaningful only above ~10 deg and let the follow-up call be the
  test; do not switch camera modes mid-station to "fix" it.
- **Deriving Arch entity ids cheaply.** `click_entity`/`hover_entity` report both `entityId` (Arch)
  and `crdtEntityId`, and within a single scene lifetime the two differ by a constant offset (one
  session measured `Arch = crdtId - 508`, verified on four separate entities). One successful
  world-aimed click therefore gives you the offset, and from then on every readout board is
  readable exactly via `get_entity_details` -> `PBTextShape.text` -- no screenshot, no
  `list_scene_entities` cross-referencing. **The offset is per-session and does not survive a
  reload**; re-derive it each run rather than carrying it over.
